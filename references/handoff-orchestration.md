# 局部交接：先理清耦合，再选 UI

可选检查，随 `1.2.0-beta.1` 提供；未加入稳定 selector，不改既有10个 adapter，也不自动重写影片。

## 这两类错误为什么会复发

1. 只有“点击/镜头/退出”几个数字被统一，字段准备、标题替换、素材预热和下一镜可读时刻仍写在不同组件。数学连续不代表每帧都有可读内容，也不代表视频第一帧已经解码。
2. 按模型能力标签选了“Computer Use＋大对号”，却没先判断证据在展示过程还是已验证的结果。输入、切换焦点等过程，应使用对应的过程 UI；没有完成证据就不画成功徽章。

## 最小编排合同

- 先看实际素材，把这一段标为 process / result / context。参考 UI 的**语义职责**、字体和材质都要匹配；不是找到一个好看的图标就完成选型。
- 用现有 `compileScore` 或等价的命名事件图管理交接。遮罩、字段布局、文字替换、相机和原片入点引用同一图；不再把秒数散落到子组件。原片的局部媒体时间仍可由明确的 Sequence from 映射。
- 同一焦点框和光标的目标几何只解析一次。下游组件只画已解析状态，不能各自重新缓动，造成一前一后。继承旧片带 time warp 的组件时，核对其时钟，不把另一条 storyAt 当 composition 时间。
- 真实视频在可见帧才挂载有首帧等待风险。选择显式 premount、与来源匹配的首帧兜底或真实 ready gate；保持原视频 from / trim / playbackRate，预热不能提前播放或改变源入点。Remotion 的 `premountFor` 只在支持它的布局/组件上用；不能直接加给 `Sequence layout="none"`。
- 退出的可读内容必须覆盖到下一内容就绪。可用同载体变化、互补遮罩或明确切镜；避免出场已经为0而进场仍为0。UI 淡出不是成功，buffer 暂停也不是阅读停顿，两者分开检查。

## 可执行检查与边界

按 `assets/handoff-contract.example.json` 写计划：

```sh
python3 scripts/validate_handoffs.py /absolute/project/handoff-contract.json --out /absolute/project/report.json
```

脚本检查声明中的时钟、几何归属、交接空档、目标可读性、媒体预热和过程/结果语义。未通过先修计划及实际接线，不降低条件、不把 result 改名绕过。返回 `contract_valid_not_visual_acceptance` 只表示计划关系成立，**不证明素材已加载、运行时不卡、UI好看或用户接受**。

随后核对实际代码与来源：组件/相机是否引用同一事件？副作用是否参与视觉计时？媒体是否有正确的预热和 source 时间？在前、中、后关键帧看焦点框/光标/文字位置，并用真实浏览器原速通过交接，记录 `waiting` / `resume` 的帧号和时长。等待日志与解码/视觉判断分开；不能为了“流畅”关闭必要的 buffering 保护来跳帧。

新增 UI 只改目标时间窗。其余镜头、原声和字体/素材保留基准 hash；关键交接和无关段落都做抽样回归。单次修复不能保证所有浏览器永不缓冲，但可把本次错误转成可检出的约束。

本地教训来自“冷挂载＋交接空档”和“过程证据误配成功UI”的工程修复。这里提供通用约束，不捆绑 Terra 文案、个人声音、特定画风或公开承诺。
